# Architecture and execution

The application is a modular monolith. HTTP/session handling lives in `app/controllers`; immutable public contracts in `hk_platform/contracts`; skill registration and task execution in `hk_platform/runtime`; model interaction in `hk_platform/ai`; business workflows/assumptions in `domains/hk_eli`; external/data/report services in `services`. No LangChain, LangGraph, Dify backend call or arbitrary model-generated SQL/code is required.

1. The request authenticates a server-verified identity, checks CSRF and selected dashboard resources, and queues an owned job. Request JSON cannot override identity or entitlement configuration.
2. In live mode Stork inventories quoted requirements and classifies all required domains using authorized skill metadata and shared reference. The planner retrieves only authorized selected Tableau assets and bounded source knowledge, then requests a typed plan covering that inventory. Rich skill guidance and shared input-schema references keep choices explicit and bounded. Requirement bindings preserve concrete task parameters/source modes, and unresolved requirements remain partial. Tableau requests also require complete/partial/no-match assessments. Fixture mode explicitly resolves Q1–Q9 to deterministic workflows; it never activates as an outage fallback. See `PLANNING.md` for semantic limits and compatibility.
3. Python validates skill versions, permissions, input schemas, task references, expected output type and the acyclic dependency graph. Generic analytical source tasks must be declared dependencies. The model selects intent; Python enforces supported capability and scope.
4. The DAG executes ready tasks with eight application-wide slots by default, two Tableau operations, two Stork calls and two active job workers. Independent branches retain valid results after non-security failures. Dependent tasks skip failed prerequisites. Cancellation stops asynchronous work; an already-running synchronous network/calculation operation drains under its own timeout. Threads are not forcibly killed.
5. Native Tableau embeds and numerical analysis are distinct skills. Native defaults send no overrides. Numerical analysis requires a reviewed export contract and downloads the complete scoped CSV, using bounded temporary disk and DuckDB memory. With `analysis=null`, one bounded Stork decision receives the actual full-export profile through a runtime column-bound schema and executes against that same export. An explicit typed analysis plan is also supported. Parameter-dependent exports and unsupported grain/fields fail explicitly. An original chart can survive a separate analytical failure.
6. Business services use fixed SQL over synthetic SQLite tables; there is no model-generated SQL. Country and currency scope are server-derived. Aggregations use exact distinct RFQ IDs, one fixture snapshot, temporal branch mappings and defined maturity boundaries. Primary-underlying worst-of flags are not full basket look-through. Metric definitions are versioned unapproved assumptions.
7. Every numerical output carries evidence with source mode, version, date, scope, dimensions, unit and calculation identity. Derived evidence records reference inputs. Generic analytical skills refuse mixed LIVE/MOCK sources and unapproved sums. Generic forecasts require a unique ordered date axis and are explicitly naive last-observation estimates.
8. Narration uses bounded evidence, not full CSV or tokens. References, numbers and min/max statistical roles are checked. Failed narration produces factual statements instead. These checks do not prove every possible semantic statement; business review remains necessary. Facts outside the sixty-record narration budget remain in the response and reports.
9. Draft artifacts contain narrative, source-mode warnings and evidence manifests. Tableau PNGs remain original exports. Generated synthetic previews are separately labeled. Downloads require current owner, permissions, resource scope and a valid TTL/hash. Reports are drafts, not automatically distributed or approved.

`var/jobs.sqlite` stores bounded-lifetime job results and trace metadata. `var/business.sqlite` stores synthetic fixtures. `var/artifacts/` stores expiring draft documents. Raw Tableau exports, Connected App JWTs and REST session tokens are not saved in job state or sent to Stork. Job results can contain authorized aggregates and must reside on restricted storage. Run `deployment/maintenance.py` periodically for expiry cleanup; reads deny expired records immediately.

SQLite deployment is **one application process / one replica**. Startup marks prior pending/running jobs interrupted, with no automatic replay. Before multiple replicas, migrate state/audit to an external database, jobs to a coordinated durable queue and artifacts to protected object storage; provide distributed locking/cancellation and shared TTL policies. Starting a second instance against the same SQLite database is unsupported.

Known capability boundaries: no approved FX conversion, payoff model, investment recommendation, historical reconstruction, arbitrary joins, automatic corporate SSO, full basket risk engine, live SPE quote contract, model-certified semantic correctness, or automatic refresh of saved insights after browser interaction. Such gaps stay explicit rather than silently producing substitute figures.
