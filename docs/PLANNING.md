# Skill selection, requirement coverage and multiple domains

Live planning has two model decisions. The first independently inventories requirements and chooses **all** applicable domains; the second chooses tasks from authorized skill descriptions and returns coverage of that inventory. This replaces the former single-domain classifier and special Tableau-plus-business flag. Fixture Q1–Q9 routes remain deterministic and explicitly do not measure live language understanding.

Every production skill now exposes a purpose, use-when/do-not-use-when guidance, illustrative typed parameter examples, capabilities and limitations. These are maintained in `domains/hk_eli/skill_guidance.py` and returned with the full schemas by `GET /api/v1/skills`. Planner prompts retain the guidance while sharing identical input schemas once by hash reference; repeated output schemas are replaced by the fixed output type. This keeps multi-domain prompts bounded without silently excluding advertised skills.

The classifier returns `domains`, `concepts`, `allow_mock_sources` and a requirements inventory. Each requirement quotes exact words in the original question, records its interpretation and kind, and may carry a concrete `expected_value`. Kinds cover measures, dimensions, conditions, periods, outputs, source modes and pricing terms. The planner must copy this inventory unchanged and produce exactly one coverage record per requirement.

- `satisfied`: identifies the task(s) providing it. Concrete values require a binding for every covered task, using a JSON Pointer into `task.parameters`.
- `unresolved`: supplies a specific reason, with no claim of execution coverage. Missing required pricing terms or unavailable source contracts can be reported this way; no invalid request or guessed input is sent to a pricing service.

For example, the condition `only KO` can be represented by expected value `["KO"]` bound to `/filters/Result`, **only if** that field/value is declared in reviewed metadata. A six-month tenor binds integer `6` to `/tenor_months`. A source requirement `LIVE` binds `/source_mode` with `target="task"`. Task-level bindings may address only source mode. String/number types and list shape are compared exactly. Shared definitions never approve the field, value, unit or entitlement.

Python checks quote provenance, unchanged inventory, missing/duplicate coverage, unknown tasks/parameter paths, expected-value mismatches, source-mode relabeling and dependency validity before execution. Exact declared Tableau controls, actual source grain/units and numerical evidence remain separately validated by their services. A model cannot invoke a skill absent from the advertised authorized menu or select a view outside discovered selected assets. Runtime results cannot change a branch's declared LIVE/MOCK mode.

All selected domains contribute their authorized skills; common analytics and artifact utilities are also offered. Mock-only source skills are advertised only when the classifier identifies explicit user authorization for mock/synthetic/indicative sources. There is no automatic mock fallback after a live outage. Tableau discovery failures are represented as unavailable source metadata, not empty financial data; the planner may mark that branch unresolved while retaining an independent valid request. Permission denial stops planning rather than exposing a denied branch's metadata.

Requirements should preserve independent per-chart/per-service filters and conditions. Separate LIVE/MOCK branches can coexist for display or a labeled draft, but generic calculations still use one declared upstream task and enforce a single source mode, unit and reporting date. No new cross-source join or bank API contract is introduced.

Responses contain `requirement_coverage`; unresolved items make the answer partial and appear as limitations. Narrators receive coverage so they cannot treat an unresolved request as a completed finding. The frontend exposes a separate requirement-coverage inspector. If all requirements are unresolved, a plan may have no tasks and returns a partial answer with reasons; this does **not** introduce a conversational clarification/resume loop or new bank API calls.

Compatibility: fixture workflows and older explicit typed plans without a requirements inventory retain their execution behavior. Their coverage is visibly `not_assessed`; they do not acquire a claim of semantic completeness. Explicit plans that supply requirements must supply valid coverage too.

Limits: structural coverage is not semantic proof. The initial model could miss a clause, misinterpret a quote, select an inappropriate but schema-valid skill, or assign a condition to the wrong task. Guidance and independent inventory reduce these risks, but real Stork paraphrase/business acceptance tests remain necessary. No successful live connection or actual-model interpretation is claimed by mock-based unit tests.

Document follow-up update: the user subsequently authorized persistent chat context and format clarification specifically for document requests. `artifact.generate` now queues document intent for the single final builder; a generic report request asks for format rather than defaulting to PDF. Saved-result follow-ups are classified separately from new analysis. General pricing/API clarification remains deferred. See `CHAT_DOCUMENTS.md`.
